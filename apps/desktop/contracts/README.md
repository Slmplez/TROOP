# Desktop client contract

The current desktop seam is:

```text
React views → ClientModels → TroopClient → fixed preload facade
            → trusted Electron IPC → Rust controllers → shared lifecycle rules
```

`execution.cjs` is the method / public DTO schema for the migrated surface. Run
`npm run contracts:generate` in `apps/desktop` after editing it. This generates
`execution.d.ts` and the marked portion of `src/preload.cjs`. `contracts:check`,
the desktop build and a contract test detect drift. The sandboxed preload contains
literal fixed channels; it does not require arbitrary local files or expose a
generic renderer-selected IPC channel.

The same schema validates input and output in `TroopClient` and trusted Electron
handlers. Requests reject unknown fields and invalid IDs. Responses validate known
public fields and permit additive fields. Rust still owns authoritative validation,
authorization, lifecycle and persistence. Rust domain structs are not generated by
this JavaScript schema; real-Core contract tests and Electron acceptance check the
boundary. Opaque model/tool payloads remain `unknown` instead of claiming a schema.

The contract covers sessions, messages, Runs, Tasks, invocations, events,
context checkpoints, the Agent selector and resource management. `resources.cjs`
defines Memory, Skills, Hooks, MCP/OAuth, providers and workspace contracts and is
merged into the same generated bindings. Resource views use `resource-facade.mjs`
to adapt their existing call signatures to ClientModels. `chat.remove` describes the desktop
confirmation result `{removed}`, which differs from the internal Core null result.

## Observation and commands

`ClientModels` is React-free. `run(id)`, `task(id)`, `session(id)` and paged queries
return shared observable models. A view reads `getSnapshot()` and subscribes to
changes. The last release stops its polling and drops pending query responses; it
never sends a business stop command. Hidden migrated panels release observation.
Selected IDs, drafts, review notes, scroll and layout stay in the view.

Each resource serializes refresh and pagination, coalesces refresh requests and
merges pages by stable IDs. Older pages cannot overwrite newer loaded records.
Run revision regressions are ignored. Published data is frozen. Core status changes
invalidate in-flight reads and cached data before establishing the next baseline.
Chat notifications invalidate queries only for the current generation and increasing
sequence. Event listeners are reference-counted alongside observations.

Run, Task and invocation detail models use **durable pull-based follow** when advertised by
Core capabilities. `agent.follow({resource, id, cursor})` returns `snapshot`,
`delta` or `reset_required`. Its cursor binds the database instance, resource kind,
ID and durable sequence; it survives a Core generation change. The frame's generation
identifies the current connection, and `from_cursor` binds each response to the
requested boundary. The client rejects old-generation responses and wrong resources.

SQLite triggers commit compact change records alongside Run, Task, invocation,
Hook, MCP-connection and execution-event writes. Each request scans at most 32
global records, returning only changes within the selected execution tree. The
cursor advances across the entire scanned range, including filtered records;
returned change sequence numbers need not be adjacent. A missing retained record,
future cursor, different scope or expired cursor requires a fresh baseline.
The replay log retains 4096 records; the original execution history is not pruned.

The initial snapshot and high-water mark share a read transaction. Catch-up pages
contain ordered change metadata and immutable event summaries. Intermediate pages
have `snapshot: null`; the final page contains the current snapshot at its cursor.
It does not pretend to reconstruct a historical snapshot at each intermediate change.
Run revisions use the existing domain revision. Task and invocation revisions use their last
durable change sequence and remain available after replay-log retention.

`FollowModel` preserves its last accepted cursor across transport reconnects,
process generations and observation release. Renderer reload establishes a fresh
baseline. Reset discards old data and requests a new snapshot; changing database
instances also clears the old cursor. Each refresh consumes at most eight replay
pages before yielding to the next polling interval. Observation release only stops
reads. Repeated or overlapping history rows merge by stable event IDs.

Large Run goal/output fields use `agent.follow-content` with the exact snapshot
revision and 4096-character pages. If the revision changes, the model keeps the
marked truncated preview and refreshes; it never mixes text from another revision.
There is no additional ephemeral token stream or push subscription in this change.
Run lists and resource management retain polling. Resource reads share QueryModel
identity and pending requests through `fetchResource`. Existing view effects and
draft state remain in the views. Chat retains notification invalidation.
`system.hello.follow_resources` advertises supported execution resources. Older
Core versions default to Run/Task follow and invocation snapshot polling.
Run follow changes refresh observed invocation/Task details and merge event history.

Commands retain the existing exact invocation epoch and start/send idempotency
identities. Identical in-flight commands within one ClientModels instance coalesce.
There is no automatic mutation retry. Disconnects invalidate completions even when
the same generation later reports ready. Structured IPC errors retain available
`kind`, `code`, `retryability`, `currentRevision`, `operationRef`, `requiredAction`;
missing backend classifications stay generic rather than being guessed from text.
Run/Task and resource commands listed in `operationCommands` use a persistent
operation journal. Before transport, the desktop saves the original UUID, storage
instance, method and ordinary input in localStorage. Sensitive commands save a
SHA-256 input digest and an empty input placeholder. Credentials remain in memory
for submission. Sensitive previews bypass query caching. On reconnect it only queries
`operations.get`. An explicit retry of a `not_found` record reuses the original
identity. Sensitive resubmission requires input from the resource form. The recovery
panel can open the associated Run or resource page and acknowledge terminal
receipts. Failure to save the local intent blocks dispatch.

For database-only commands, `operations.execute` atomically commits the receipt and domain changes in SQLite.
An identical command returns its original receipt; changed parameters conflict.
Start/resume activation and cancellation signals occur after commit. A committed
receipt means command acceptance, not successful execution or exactly-once external
effects. Rejected receipts remain stable; a revised intent requires a new operation.
The current trusted local desktop principal is supplied by Core. Remote service
authentication is not implemented. Receipts are retained without automatic expiry.
Resource commands involving credential storage or runtime signals first commit an
external-operation intent. The receipt starts as `needs_reconciliation`. Completion
stores the result. A crash, effect failure or receipt-write failure preserves the
intent for inspection. Reusing its ID returns that receipt and never repeats the
effect. Inspect resource state before closing the record or issuing a new intent.
This conservative path also retains validation errors for inspection.

Electron preserves native provider/workspace/MCP removal and Windows stdio enable
confirmations. Canceling a dialog returns `dismissed` and clears the local pending
entry. New resource command channels require the operation ledger. Legacy fixed
channels remain available for compatibility. Chat writes retain their existing adapter.

`allowed_actions` projects Run stop/resume/steer/compact, invocation approval/review
and Task stop/review availability with reasons. Shared lifecycle checks and Worker
evidence drive reconciliation projections. Commands validate current facts again.
The approval UI also matches invocation detail and summary revisions before enabling
submission. Older responses without action projections retain the prior fallback.
The database schema is 15 and the wire protocol remains 10.

## Authorization management and evaluation

`authorizations.list/get/history/evaluate` expose saved grants, revision history and
scope previews. `authorizations.save/revoke` use the existing operation ledger with
an exact `expected_revision`. Revision conflicts retain `currentRevision` through
the receipt and ClientError. The authorization page uses the shared Client Models,
and older Core versions expose the page as unavailable through capability checks.

Grants bind purpose, Agent, engine, Windows host environment, projects, workspace,
read/write roots, operations, network scope, expiry and optional rule identity.
Evaluation checks current facts and canonical targets. Its `allow` decision means
the requested scope fits. Standalone previews return `executable: false`. The native
dispatch compiler creates an executable permission plan for supported file tools
after checking the actual invocation arguments. CLI and arbitrary Shell execution
require verified execution capabilities. Each grant revision retains its latest evaluation with the action,
normalized target, time and effective scope. Subsequent evaluations replace that
revision's previous preview.

Saving and revoking grants, lost-response recovery, reloads and scope previews are
covered by `test/authorizations.test.cjs` and the real Electron workflow
`scripts/authorizations-smoke.mjs`. Local evidence is in
`verification/c3-authorization-01-2026-11-07/` at repository root.

## Native execution and internal event rules

`engines.capabilities` describes the current `native-files-v1` capability set.
`agent.start` accepts an optional `authorization_id`, explicit `project_ids` and
`rule_management_authorization_id`. A supplied `action` selects `tool_action` and
allows omission of the model provider. Direct actions require `operations.execute`.
The existing Run, Invocation, Worker receipt, stop and reconciliation paths own the
execution. Direct actions reject steer and context compaction.

Bound execution rechecks the grant at dispatch, Worker Ready, and while active.
Grant revision changes, expiry and revocation stop further protected work. Native
controlled tools currently cover read_file, write_file, list_directory and
search_text. Explicit Shell bindings admit contained commands and background
Tasks. Prompt and command Hooks require fixed authorized revisions. MCP grants
bind the service revision, identity, tool and complete arguments. Stdio additionally
selects full-host or contained execution, with initialization scope in the evidence.
The existing manually controlled execution path retains its behavior.

Pi 1.5.0 supports explicit text-only and Windows contained native modes. Native
mode uses read, PowerShell, edit and write tools with the granted directory roots
and network `any`. The process and native tools share that network authority.
`credential_env_keys` records explicitly selected API-key/token variable names.
Values pass in memory to the engine and its tools. A single-use configuration
directory is created inside an authorized write root, with the existing built-in
model selection captured from an authorized settings file. Stored credentials and
custom provider configuration require separately supported integration. The
permission plan exposes the SDK, model-selection source digest and runtime paths.

`rules.list/get/history/save/simulate` expose versioned internal event rules.
Save uses the operation ledger. Registered events are `run.completed` and
`run.failed`, with workspace and optional source Run conditions and finite expiry.
Actions use a fixed native Agent start or a direct tool start. Parameters are fixed
in the rule revision. The initial editor exposes typed configuration through JSON.

Core records a per-rule Run/epoch semantic identity and commits accepted dispatch,
the new Run, trigger evidence and delivery together. Stored executions recover
through the existing reconciliation path. Rules retain their event baseline,
revision authors and grant references. Workspace dispatches share a versioned write-limit policy. The default remains
a conservative three-per-hour limit and sixty-second cooldown, counted in a
ledger keyed by source, object and action, with a workspace ceiling of the same
numbers. Automatic chains stop at depth eight. Agent `manage_rule` requires a separate rule-management grant and checks
both original and proposed scope, current project membership, operation and expiry.

Observed rule and authorization reads use shared polling and release it on final
unsubscribe. Rule history pages contain up to five revisions and five deliveries.
Run details expose kind, trigger, chain and the invocation permission plan.
Evidence is in `verification/c3-execution-2026-11-07/`.

## Tests

`memory.maintenance.get/save` expose independent per-Agent maintenance settings.
Save requires the operation ledger and exact settings revision. Enabling records
the selected provider, model and destination for private-memory maintenance.
Unconfigured jobs enter `waiting_configuration`. Queued jobs retain their evidence
across restart and can be cancelled before configuring a destination.

The first model request freezes provider configuration, credential reference and
settings revision for the attempt. Extraction and validation share that snapshot.
Provider destination changes invalidate it. Disabling maintenance authorization
commits cancellation before aborting active model requests. Late callbacks cannot
apply results. Manual retry chooses current settings and retains prior attempts.
Public job details include the twenty most recent attempt summaries and omit raw
configuration and credential references. Legacy jobs retain their original model
evidence and require current independent settings for retry.

An active forgetting guard adds an independent validation stage for new facts in
the authorized target scope. Rejected or uncertain proposals remain in
`waiting_review`. Direct Agent writes use the same job queue and keep their
invocation provenance and protection after validation. `forgetting_check` reports
guard coverage. Incomplete bounded snapshots require review. The configured
maintenance model receives the authorized forgetting reference text for this check.
Job details subscribe through Client Models, including cancellation updates.

Rule definitions accept `Start | CliStart`. CLI simulation and execution share
the same launch preflight. A rule-bound CLI grant is checked again at dispatch,
and the resulting external Task uses the normal sealed-evidence review contract.

Claude and OpenCode launch grants accept an explicit `model_settings` source
binding. Saving computes its canonical path and fingerprint. Each engine selects
only its admitted model fields in memory. A changed source invalidates the grant.
OpenCode 1.19.5 also refuses existing ancestor configuration files outside the
read grant before dispatch and during authorization monitoring.

The memory page includes a dedicated maintenance model form. Evidence is in
`verification/c5-maintenance-2026-11-07/` at repository root. This slice covers model
configuration and attempt ownership within C5.

- `node --test test/client-models.test.cjs`: isolated clocks and delayed transports
  exercise the public observation/command interface and failure races.
- `node --test test/client-contract-core.test.cjs`: real Core DTOs and the race
  between a previously available resume action and another observer's cancellation.
- `test/client-types.mts`: positive types and rejected method/ID/epoch/source inputs.
- `test/resource-client-core.test.cjs` checks real resource DTOs, duplicate writes,
  atomic rollback, uncertain credential effects and expired approval follow.
- Existing Agent, Task and chat tests plus eight Electron smoke workflows exercise
  the real preload, trusted IPC, Core, streaming output, stop and reconciliation.

## CLI interaction contract

`cli.interactions` and `cli.interaction` expose persisted requests, effective actions,
fixed DTOs and independent delivery facts. `cli.respond` uses the command journal.
`cli.preview` returns a permission-plan digest and any linked-task scope changes.
The Core revalidates that digest at `cli.start`. Host plan consumption is
`host_recorded`, while native transport writes are `written`.

The supervisor defaults to a 30-second RPC wait to cover fingerprint validation of
large native CLI programs. RPC wait time and the execution/startup/human-wait
limits have separate meanings. A lost RPC response remains an operation-recovery
case. It never causes an automatic execution retry.

## Shared work item contract

`work_items.list/get` expose a work item's stable identity, revision, owner Agent,
optional project, workspace, goal and acceptance conditions. List queries use
bounded ID-keyset pagination and filter the persisted records by Agent, project,
workspace and archive state. Schema 24 adds the work item table.

`work_items.save/archive` require the operation ledger. Updates require the exact
work item revision. Creation allocates identity in the receipt transaction.
The Core validates Agent, workspace and project membership and returns separate
save, archive and restore availability. Archived records remain readable.

The work item Client Model refreshes the loaded pages as a replacement collection
so membership changes remove old rows. The board preserves local dirty drafts,
fences stale revisions, displays the selected workspace path, and uses the same
command journal as other resources. W1 manages work definitions. W2 adds execution
associations and acceptance projections.

Schema 25 adds stable Work Item / Run associations. `work_items.start` freezes
the work definition and commits the Run, link and receipt before activation.
Agent, workspace, project, goal and acceptance conditions come from the work item.
Native and CLI launch inputs form a discriminated union. CLI launch first confirms
the plan returned by `work_items.preview` through the existing CLI preflight.

`work_items.runs` uses Run-ID cursors and a 30 KB serialized public-result budget.
Unsealed CLI evidence hashes are nullable. Pages expose bounded result summaries
and the accepted definition, Run revision, evidence hash and note. Full evidence
uses the linked execution detail. The Client Model refreshes every loaded page.

`work_items.accept` checks the current definition, Run, execution revision, hash,
cancellation generation, references and dependencies. External CLI results also
require their existing fixed-evidence review. Native work acceptance records an
explicit user note. Definition edits invalidate completion for the new version.

`work_items.cancel` fences future work and stops the associated execution through
the existing owned-task tree. Delayed output cannot reopen cancelled work.
Stopping the current Run and cancelling the work remain separate commands.
Dependency edges reject cycles and release only after the current prerequisite
definition has been accepted. W1 database records receive compatible defaults.

## Group chat contract

Schema 26 adds groups, immutable user messages and unique per-target deliveries.
`groups.list/get/messages/deliveries` expose ID-cursor pages and resource actions.
`groups.preview` shares candidate selection and admission with `groups.send`.
Structured Agent-ID mentions suppress ordinary active-listener fallback. Reply
targets are validated in the same group. Broadcast includes passive members.
Textual @ characters remain message text. The Core binds the user sender.

`groups.save/archive/member/send/resolve_delivery` require the operation ledger.
Configuration updates use group revisions. Delivery decisions use delivery
revisions. Message creation and recipient records commit together. A separate
client message ID recovers the original immutable fact with the same content and
targets across configuration revisions, without recalculating old deliveries.

Receive disablement, removal, listening changes, pause, archive and scope changes
cancel affected pending deliveries. Project membership revocation cancels them in
the membership transaction, including legacy entry points. Restart moves queued
deliveries to `waiting_resume`. Explicit resume rechecks current eligibility.
Group limits are 32 members and 128 pending deliveries per group/Agent pair.
Overflow records the retained message and delivery refusal.

All group pages use bounded serialized public DTOs. Client Models refresh loaded
pages so membership changes and old delivery decisions become visible across
windows. The UI preserves per-window settings/message drafts and fences stale
settings. G1 records delivery readiness. G2 adds actual Agent consumption, trusted
Agent replies, Run associations and adoption evidence.
