# Agent 执行、恢复与并发契约

状态：2026-11-01 用户已确认四项产品取舍；本轮契约基线。唯一任务状态源：[确定 Agent 执行状态、恢复和并发契约](https://github.com/Slmplez/TROOP/issues/4)。本文不实现 Rust Core，也不宣称旧系统与新系统已经等价。

已确认：异常退出后先核对再手动继续；停止整个所属任务树；同工作区写操作串行；普通补充指令在安全边界处理，立即停止另有操作。

## 1. 范围与既有约定

覆盖一次任务从接收、模型流、工具调用、等待、补充指令、子代理、压缩，到取消、退出和重启后的核对。模型和工具可替换，但生命周期、持久性与授权检查不能依赖 UI 是否仍连接。

已有决定保持：关闭窗口托盘驻留；显式退出停止任务和调度；旧 Grok Bot 历史不续跑；本机桌面锁屏只暂停受影响动作，解锁重新观察，不重放旧输入。这里的恢复只讨论未来 TROOP 自己记录的任务。

## 2. 对象与身份

| 对象 | 责任与边界 |
|---|---|
| Conversation | 展示消息、草稿与相关执行；不是执行线程，也不是权限主体 |
| Run | 一次被接收的任务执行，有触发来源、输入版本、模型预算、父 Run 与生命周期 |
| Task | Run 拥有的异步作业，例如后台命令或子代理作业；必须有 owner，不因界面消失成为无主作业 |
| ToolInvocation | 某次不可变工具请求及其投递、执行、结果和副作用确定性 |
| Approval | 对特定操作快照、权限范围和有效期的决策；不是可复用的任意执行开关 |
| InputRequest | 对特定 Run / 步骤提出的问题，具有自身 ID、版本和过期条件 |
| Checkpoint | 已提交的状态引用与事件游标；不包含“尚未证明已落盘”的增量 |
| CompletionNotice | 某个作业的完成通知；需要先存储、再消费，不是直接触发新模型调用的临时 callback |

Conversation ID、Run ID、Task ID、Invocation ID、Approval ID、RPC request ID、幂等键与进程 generation 分离。Run 恢复不换逻辑 Run ID，但增加执行 epoch；每次模型请求和可重试投递另有 attempt ID。终态 Run 再次执行产生关联的新 Run。

## 3. 生命周期：阶段与等待原因分开

持久阶段使用 `queued / running / waiting / recovering / cancelling / completed / failed / cancelled / interrupted`。

`waiting` 另带等待项集合：`input / approval / tool / background / resource / desktop_unavailable`。同一 Run 可以同时有后台子任务和一个输入问题，不能用互斥的 waiting_input / waiting_tool 状态覆盖事实。UI 可按优先级呈现主要原因，但完整等待集合可查询。

| 当前阶段 | 条件/事件 | 下一阶段或行为 |
|---|---|---|
| 无 | 接收合法 start 并持久化幂等键、输入与 Run | queued；提交成功后返回 Run ID |
| queued | 获得执行额度，确认未取消 | running |
| running | 出现阻断当前推进的等待项 | waiting；异步作业仍可独立推进 |
| waiting | 所有当前阻断项解决且 epoch 有效 | running |
| 任意非终态 | 请求取消 | 持久化取消意图并进入 cancelling；先停止新派发，再停止所属受管作业 |
| cancelling | 受管作业已核对停止或完成 | 按已提交终止意图进入 cancelled（cancel）或 failed（failure）；保留已发生副作用及不确定项 |
| cancelling | 不能确认受管作业停止 | interrupted，原因 stop_unconfirmed；相关资源不能当作空闲 |
| running / waiting | 成功条件已满足，且没有待消费动作、待处理完成通知或仍归属本 Run 的活跃作业 | 才可 completed |
| 任意活动阶段 | 持久状态提交失败 / Core 失去控制权 | 停止新派发；可写时提交 interrupted，否则只报告存储故障并在重启核对最后已提交记录 |
| 发现遗留活动记录 | 重启核对 | recovering：核对 Worker 账本、受管进程与已提交结果 |
| recovering | 核对完成，无取消/失败终止意图 | interrupted，显示待处理项目，必须手动继续，不自动推进 |
| recovering / interrupted | 存在取消/失败终止意图 | 继续停止核对；不能 resume；确认停止后分别 cancelled / failed |
| interrupted | 无取消/失败终止意图，合法手动 resume + 核对通过 + 新 epoch | queued；不重新派发已成功或不确定的旧调用 |
| running / waiting | 确认当前任务无法完成 | 持久化失败终止意图，停止派发并进入 cancelling 清理；停止确认后 failed，否则 interrupted(stop_unconfirmed) |
| completed / failed / cancelled | 收到旧输入、旧审批、迟到 wake | 记录为迟到证据，不重新激活 Run |

`interrupted` 是可审查的挂起状态，不等同失败或取消。`failed` 表示已确定无法按当前任务契约完成，清理归属作业后终结；显式重试创建新 Run。模型发出最终文本不自动代表整个 Run 已结束，活跃后台工作必须仍可见、可停止。

终止意图与阶段分开持久化，至少区分 cancel、failure；一旦提交，不被进程重启、补充消息或 resume 清除。取消与失败竞争由 Core 的持久顺序裁决，保留另一事件作为证据。`cancelling` 表示停止清理阶段，UI 根据原因显示“正在停止”或“失败后清理”，不把失败误称用户取消。

显式退出先关闭新任务入口和调度，再停止全部活动任务树；退出停止流程不自行设置 cancel/failure 意图。未完成且无取消/失败意图的执行保存为 interrupted(shutdown)，下次启动核对后手动继续；已取消者仍保持取消意图。宽限期结束时，未确认停止的受管作业保留 stop_unconfirmed 与资源隔离记录；窗口/进程已退出不代表远端作业已停。关闭窗口到托盘不触发这一流程。

取消不撤销此前文件修改或外部请求；cancelled 也不等于副作用归零。若远端效果未知，ToolInvocation 保持 indeterminate，报告明确显示；若本地/Worker 作业是否仍在运行都未知，Run 不得显示“全部已停止”。

## 4. 工具状态与提交边界

工具至少区分 `prepared / dispatched / running / succeeded / failed / cancelled / indeterminate`。prepared 是已持久化的调用计划；dispatched 是已经开始交付，尚未收到回执也可能已执行。

派发顺序：冻结工具/参数/环境与输入版本 → 记录 Invocation 和授权状态 → 获得资源租约 → 执行前重验 epoch、审批、前置条件 → Worker 接收并记录 → 执行 → 保存结果/产物 → Core 提交业务结果及事件 → 发出持久完成通知。任何跨进程“发送成功”都不代替结果提交。

- 重复命令以 Invocation ID 查账，禁止无条件重跑。attempt ID 表示同一调用的一次传输尝试，不能让重试意外变成新调用。
- Core 在派发前崩溃：核对无接收记录才允许按现有调用重投；仅凭本地状态 prepared 不够。
- Worker 已执行、结果回传丢失：按原 ID 查询账本，不重新执行。
- 工具可能对外产生副作用但无法确认：indeterminate；不自动以失败重试。新尝试需要新的明确决策与关联记录。
- 只有工具适配器声明且可验证的幂等机制，才允许受限重试；Shell/MCP/HTTP 不统一承诺 exactly-once。
- 取消与完成竞争：Core 持久顺序确定接收规则；迟到成功可以用于记录已发生效果，不得恢复已取消的调度或触发子步骤。

## 5. 输入、授权与补充指令

普通补充指令首先以 message ID 持久化。每次采纳记录 input revision；安全边界包括模型步骤之间、工具结果核对之后、准备下一次工具调用之前。已启动的写操作不因普通消息被强行中断；另有显式停止动作。

在派发前到达的指令若改变已有工具计划，应废弃旧计划或重新校验；不能将“批准旧参数”的审批移用于新参数。模型产生的半截工具 JSON 只作临时展示，不创建可执行调用。

InputRequest 和 Approval 回复都要求 request ID、Run ID、版本、有效状态；重复相同回复幂等，矛盾回复返回冲突，迟到回复拒绝并说明原因。用户输入等待不等于授权；普通“继续”文本不等于批准全部待审批工具。

同会话只允许一个主动推进的模型步骤；补充指令与新任务请求要有不同命令语义。跨会话有界并发；同一 Run 不应在等待用户输入时继续执行依赖该输入的动作，无依赖作业是否继续应由依赖图确定。

## 6. 父子任务与后台完成

所有子代理/后台 Task 记录 ownerRunId、parentTaskId、目标环境、预算与取消范围。子代理有自己的 Run 和上下文，不以复用父 agentId 替代身份。默认不允许隐式脱离所有权；独立任务由单独创建的 Run 表达。

子代理 Task 与 childRun.ownerTaskId 建立唯一关联，归属关系必须单一、无环。取消沿持久归属树传播，提交取消时关闭该树的新派发。创建子节点、转移归属和取消由 Core 串行事务裁决；终止中的任务树禁止通过分离逃逸。通知投递到记录的 owner，并核验归属版本。权限及预算只能在父授权范围内收窄，不能因新 child Run 获得额外权限。

完成通知采用可持久核对的 inbox/outbox：结果先提交，通知拥有稳定 completion ID，父方提交“已消费标记 + 接纳结果 + 下一动作”后再确认。重连重复投递不重复启动模型；不能在唤醒前删除唯一持久标记。

- 父 Run 等待子任务：完成通知解决对应等待项，满足条件才继续。
- 父 Run 正在模型步骤中：通知入队，在安全边界采纳，不并行启动第二个模型请求。
- 父 Run 正在 cancelling、recovering、interrupted 或已终态：持久接纳子结果和迟到完成证据，不启动模型或派发后续动作；核对可以使用这些证据，推进仍须合法手动 resume。
- 重启找不到旧子作业：标为状态未知/中断，不伪造完成，不从旧命令盲目重建。
- 父 Run 的失败/取消向仍归属它的作业传播停止；人工分离为独立任务必须显式改变所有权，不在退出时自动分离。

## 7. 工作区并发与资源控制

默认同工作区写操作串行。普通读可并行，但要清楚读到的版本；可实施检查的文件/补丁适配器在读后写时校验内容哈希或补丁前置条件，失败返回冲突。不能承诺任意 Shell 自带此保护；界面需区分这种限制。

任意 Shell 默认视为可能写入整个工作区，持排他写租约；不能仅按命令名称猜测只读。Git index / checkout / merge 需要仓库级排他。外部用户或程序不会遵守内部租约，因此支持前置条件的文件/补丁适配器仍须版本校验；Shell 不能据此承诺与外部编辑安全并行。

资源身份规范化必须处理路径别名、重叠目录和 Git 共用管理目录，不能只按显示名称或 cwd 加锁。任意 Shell 可能写到 cwd 外：受控写入范围须由执行环境限制或扩大冲突域；无法限定的宿主命令使用宿主执行域排他，并明确其无法隔离外部程序写入的限制。范围外写入不因工作区租约获得授权。

需要并行修改时使用独立目录或可选 worktree，非 Git 工作区不能强制依赖 worktree。隔离结果回到目标工作区仍须授权、前置条件与冲突处理；不能将独立目录等同安全沙箱。

对多个受控资源按固定顺序申请或通过统一调度器一次授予；等待资源不占据模型推进槽，也不得无限持有不相关资源。后台命令继续写入时，资源租约不能因前台工具返回“已转后台”而释放。停止无法确认时保留资源隔离状态，避免下一作业并发改写。

租约到期不证明旧进程已经停止写入。资源隔离状态必须持久化，重新授予前核对旧执行已经停止或被有效隔离；隔离目录仍可能共享远端目标与 Git 元数据，不能忽略这些资源。

同一桌面单控制者及租约失效后的输入处理遵守既有约定；具体宿主/Docker 控制协议和授权实现交由后续双桌面任务验证，本任务不提前宣布其后端已可用。

## 8. Core、Worker 与 UI 的权威边界

Core 是 Run/Task/审批/输入/资源归属及业务事件的单一写入方。Worker 账本记录“是否接收、是否实际执行、结果和进程身份”，用于核对事实；它不自行批准操作，也不替 UI 终结业务任务。分布式事实无法确认时保留 unknown，不让一方覆盖另一方证据。

每条命令有 protocolVersion、requestId、idempotencyKey、Run/Task/Invocation ID、workspace、target、epoch、权限版本与资源租约引用。具体字段按命令裁剪，不能将 renderer 输入的身份/权限当可信事实。

Worker 持久维护已接受的 fencing epoch，在接收新派发时拒绝旧 epoch；原 Invocation 的查询可以返回历史结果，不能再执行。Core 单写权取得、Worker fencing 生效、资源重新授予具有明确顺序；无法确认旧 Worker 停止或隔离时不得在同资源开启新写入。取消传播有时间窗口：Worker 已接收的操作仍需停止/核对，不能以 Core 已提交取消宣称远端立即停止。

持久事件至少包含 eventId、对象 ID、事件序号、executionEpoch、causeId 与版本化 payload。UI 快照带游标；缺口补拉，游标过旧重新取快照；旧 generation 的流增量丢弃。worker 迟到结果可进入核对通道，不能被当作新执行命令。

RPC 超时只表示响应未收到；重试 runs.start 返回原 Run；runs.cancel 的接收回执不冒充“已停止”。断线不会取消业务操作，取消必须显式发出并查询状态。

持久存储失败时禁止再派发有副作用工具。当前源码的 best-effort checkpoint 行为只作迁移事实，不能直接成为新 Core 的持久承诺。

## 9. 持久与临时内容

必须持久：被接收的输入、Run/Task 状态、完整工具参数、审批快照、派发意图/回执、资源所有权、最终结果/产物引用、完成通知及消费标记、压缩版本和来源游标。

临时：token delta、未完成的工具参数片段、画面帧、心跳、可重建的进度指示。临时内容可合并/限流，不得拖住取消与控制消息；崩溃后缺失增量不能伪装为完整已提交消息。

压缩使用不可变已提交快照；保存 summary 与覆盖的输入/事件版本。压缩期间到达的新指令、审批/工具结果不能被旧 summary 覆盖；版本不匹配则重新计算或保留追加内容。压缩失败不能删除原历史。原始工具调用与结果仍通过稳定 ID 关联。

## 10. 验收边界（待规格转任务）

| 场景 | 需要观察的行为 |
|---|---|
| start 响应丢失后重发 | 同幂等键只产生一个 Run，返回原状态 |
| 半截工具参数 / 输入纠正 | 不提前执行；旧审批不适用于新参数 |
| stop 与完成同时到达 | 记录真实效果，不启动后续工具；不承诺撤销副作用 |
| Worker 收到调用后断线 | 按 ID 核对，不盲目重发 |
| Core 在不同提交点崩溃 | 已提交状态一致；无法确定的调用明确 indeterminate |
| 父/子进程重启、重复完成通知 | 不丢唯一唤醒，不重复模型推进；终态父任务不复活 |
| 输入等待/审批等待/锁屏并存 | 分别解决等待条件，不把输入回复当作解锁或授权 |
| 同工作区并发改写、用户中途编辑 | 写租约排队；支持前置条件的文件/补丁适配器遇冲突不覆盖，Shell 的外部并发限制可见 |
| 后台命令仍写入 | 写租约归后台 Task 持续持有，不能前台返回就释放 |
| 压缩与新消息并发 | 新消息不丢失，摘要覆盖版本可核对 |
| UI 重连/事件积压 | 快照游标无缺口，持久终态不丢，控制不被输出阻塞 |
| 显式退出与重启 | 停止所属受管作业，持久化未完成状态，不退出后继续调度 |

## 11. 本轮证据

用户于 2026-11-01 确认本文四项默认取舍。两位子代理分别检查 Agent 注入/回放入口与取消/子作业源码；后者另复审本文竞态，已修正取消意图被 resume 绕过、停止确认、跨子 Run 归属、旧 epoch 和重叠资源边界。

### 受控动态回放

`replay.mjs` 加载真实 AnysphereAgent、SimplePromptToolExecutor、生成的协议类型和 InMemoryBlobStore，只替换底层模型流与工具副作用；禁用网络 fetch，阻断外部资源访问。`replay-results.json` 保存人工输入轨迹。

| 场景 | 实际观察 | 证明边界 |
|---|---|---|
| 文本完成 | 真实 Agent 返回完成，回调收到 checkpoint | 人工模型输出，内存存储 |
| 工具循环 | 第一模型步产生工具调用，工具返回后进入第二模型步 | 人工无副作用工具；非真实文件/Shell |
| 工具等待 | 等待期间保存 pending 调用，释放后继续 | 等待工具不等于已验证审批或用户输入等待 |
| 工具取消 | 取消信号到达工具，runStream 以 ConnectError canceled 结束 | 非进程树终止验证；无远端副作用 |
| flush 故障 | 真实 createRunStreamStateUpdateWithFlush 吞掉人工 flush 异常，未调用外层 checkpoint，调用方仍返回 | 现有 best-effort 行为，不可继承为可靠提交保证 |

回放不覆盖真实提供方、真实工具生命周期 UI、SQLite、进程崩溃、压缩/审批闭环或 Rust 实现；生成的 bundle 不进入发布证据。

### 源码核对与有意改变

- `source/host/runner/turn-run-shell.ts`、`turn-settle.ts`：取消信号、generation 和 checkpoint/final-state 门控分别存在；发出 abort 不保证最终状态提交或受管进程已停止。
- `send-turn-dispatch.ts`：已有 host 新消息路径 supersede 当前执行。新契约按用户决定改为安全边界采纳普通消息，不宣称这一点与旧行为等价。
- `subagent-runtime.ts`：会话、运行中 promise 与 steer 队列部分在内存；待处理 steer 会被后续同子代理消息覆盖。新契约要求持久输入逐条接收、可追踪消费。
- `sand-pending-wake-store.ts`、`completion-revivals.ts`：现有持久 wake 标记不等于可靠消费事务；消费顺序与故障观察见下节。
- `pending-wake-rearm.ts`：进程内子作业失踪时给出未知最终状态，而不是自动证明续跑；符合需要人工核对的方向。
- `summarization-orchestrator.ts` 与 `abstract-user-message-action-handler.ts`：存在压缩与输入处理路径，但尚无真实持久并发回放证明；新契约的不可变快照/版本规则须由后续实现验收。

### 后台完成通知的受控故障回放

`wake-replay.mjs` 调用真实 SandPendingWakeStore、PendingWakeRearm、CompletionRevivals，使用新建的隔离磁盘目录，仅宿主服务和 runner 为人工夹具。五个场景断言通过，完整顺序见 `wake-results.json`：

- shell 成功对照：执行一次，marker 和队列清除。
- shell runner 抛错、subagent runner 抛错：runner 开始前 marker 已清除；失败后队列为空，第二次 drain 不再尝试。
- session 不可用：marker 与队列清除，runner 未调用。
- execution disabled 对照：marker 与队列都保留。

这证明该消费路径在上述失败后自身不重试，支持采用“提交接纳后确认”的新契约；不能据此推断全系统永久丢失。完成项直接注入队列，未覆盖发现机制、启动重建、进程崩溃、fsync/断电或真实并发。

## 12. 后续验证归属

上述条款是实现必须满足的目标，不能作为已经通过的测试。最终规格与发布门禁任务必须承接：进程终止点故障注入、Worker 账本去重/fencing、SQLite 提交/磁盘失败、父子完成通知重复/丢失、压缩与新输入竞态、退出/锁屏与租约隔离、真实提供方与进程树停止。双桌面技术可行性继续由已有宿主及沙箱原型任务验证；自动化错过触发与重叠策略由集成/调度决策任务确定。
