# 历史导入：恢复等级与报告原型

状态：**用户授权按最佳方案处理后确定的决策原型**，对应 [验证旧历史恢复等级与导入边界](https://github.com/Slmplez/TROOP/issues/3)。不是生产导入器，也没有导入用户的真实历史。

打开 [history-import.prototype.html](history-import.prototype.html) 即可操作，无需安装、构建、服务器或网络。所有状态在内存中，刷新清空。该原型与生产 Agent 存储代码的对应位置是 `source/packages/agent-kv` 与 `source/host/extensions/session`；按本次工作约定，临时产物集中保存在 `.scratch/troop-history-import/`。

## 要回答的设计问题

在已确认“不续跑旧执行”的前提下，让用户看清哪些历史恢复了、哪些没有，并避免重复导入、覆盖版本或重放旧工具。原任务中的“完整、部分、可读不可续跑、失败”不应是四个互斥状态：完整历史也不能续跑旧执行。

建议分为两条独立状态轴：

| 状态轴 | 值 | 含义 |
|---|---|---|
| 内容完整性 | 完整 | 所选一致快照中，声明支持的内容与依赖均已验证；不表示找回快照之外的历史 |
| 内容完整性 | 部分 | 部分消息可读，但有附件、关系、未知字段或来源覆盖缺口；列出具体缺失 |
| 内容完整性 | 无法恢复 | 当前来源不足以得到可读会话，例如根缺失、关键内容损坏或密钥不可用 |
| 执行能力 | 仅历史，不续跑 | 所有导入结果都适用；创建新任务时不继承旧授权、pending 调用或运行状态 |

“仅文本可读”是部分恢复的说明，不额外引入可续跑等级。数据库快照不一致应先归为“来源待修复 / 禁止导入”，而不是把暂时读到的记录数当作成功。原型把阻断原因展示在“无法恢复”预览中；正式 UI 可将来源错误与记录恢复结果分层。

## 可操作场景

页面提供十组引导与自由操作按钮：完整历史、缺失附件、没有原密钥、子代理未完成、重复与新版本、未知字段与文本、固定槽与坏快照、失败与回滚、不同来源与父关系、损坏与缺根。

建议先看“缺失附件”“重复与新版本”“失败与回滚”。每次改变来源，预览与部分恢复确认失效；扫描和准备均不写入目标区。提交故障只模拟内存模型，没有声称实现数据库崩溃恢复。

## 确定的导入规则

1. **保留原件，先做快照。** 读取用户指定的副本或一致导出；不得用会自动迁移、修复或隔离原库的旧构造器直接打开原件。不要通过“拷贝主 db 文件”假定包含 WAL 中的已提交记录。
2. **检测来源与适配器。** 区分旧 store.db、conversation-blobs.db、路由文本 JSON、本地明文 blob 和已识别加密 envelope。来源不明时标为未知，不以解析失败猜测“这是密文”。
3. **严格检查原始元数据。** 校验 JSON、hex、字段存在性和根寻址类型；不调用会补随机密钥的旧反序列化器来判断原密钥是否存在。来源命名空间应稳定绑定原数据集，不使用会因搬文件而变化的路径。
4. **根与内容校验分开。** 内容寻址 blob 核对明文 SHA-256；固定根槽按已识别槽定位，其内容另记哈希。不能要求固定槽 ID 等于内容哈希；密文文件校验与解密后内容哈希也不能混为一谈。
5. **完整引用清单。** 消息、步骤、工具结果、附件、摘要及归档、父子状态和引用均需盘点；未知对象保留原 bytes。GC 遍历故意跳过某些历史回链和摘要归档，不能作为完整导出遍历器。
6. **预览明确缺失。** 输出来源总数、可读数、缺失/损坏/不可解密/未知数，带对象与引用位置。不能因旧 API 静默跳过缺失项而显示“完整”。部分恢复需要用户看过本批清单后确认。
7. **稳定 ID 和版本。** `(sourceNamespace, objectKind, legacyId)` 识别来源对象；同对象、同规范化内容版本重复导入跳过。同旧 ID 不同内容保留新 revision，与旧 revision 并存，不覆盖。界面按同一来源会话分组，新版本加入后当前版本保持不变，用户查看内容及缺失差异后选择当前版本。不同来源没有明确关联时分别导入，不按文本、标题或时间近似自动合并。
8. **关系延迟解析。** 保存原 parent/child ID 和批次内映射；父对象缺失时保留未解析关系。之后补充资料可产生新 revision 或已验证的关系补全，不猜测映射。
9. **批次原子提交。** 目标区统一写入历史对象、映射及报告；准备阶段取消不改变目标区。故障不留下“导入成功但映射缺失”的半批状态。生产事务/中断恢复仍需后续实现验证。
10. **旧执行不恢复。** pending 调用、审批、未完成状态保留为历史证据。用户选定可读版本后可以创建全新任务草稿；草稿绑定所选历史版本，不默认取最后导入版本；不自动提交任务，不重放旧操作。

本原型不实现跨来源自动合并或就地覆盖旧版本。页面版本 A/B 与变体签名只是演示标识，不是生产哈希契约。

## 中间导出格式草案

建议外层为带版本的 JSON 清单，原始 proto/未知 blob/附件在独立只读资料区，展示对象作为派生数据。密钥只使用本地密钥引用，不序列化进报告、JSON 或可分享包。

| 字段组 | 必需信息 |
|---|---|
| 格式 | formatVersion、adapterId / adapterVersion、生成工具版本；未知版本停止解释并保留原件 |
| 来源快照 | sourceNamespace、snapshotId、文件种类、相对路径、文件哈希、数据库一致性状态、原数据版本（未知时明确标记） |
| 原对象身份 | objectKind、legacyId、原 parent / child refs、来源记录位置 |
| 根定位 | addressing=`content-hash` 或 `fixed-slot`、原 root ID、原始内容哈希 |
| 展示派生 | 消息、步骤、摘要、附件元信息、已解析关系、历史执行状态；不能替代原件 |
| 原始内容 | originalRefs 指向原字节；明文/已识别 envelope/未知分类；解密后类型与哈希；密钥仅本地引用 |
| 完整性 | integrity、问题代码、对象位置、原始错误类别、缺失引用；来源覆盖限制与 unknown 字段列表 |
| 导入映射 | 稳定来源键、规范化内容 revision、目标 ID、同源重复/版本冲突/关系未解析、批次 ID |
| 执行约束 | execution=`historical-only`；不导入活动审批、运行锁或自动恢复计划 |

[intermediate-example.json](intermediate-example.json) 是三个基线样本的**简化示例**：包含原 blob、来源根、派生文本、附件/子代理引用和 pending 列表。没有实现完整清单规范、所有 proto 分支或生产 importer。示例 revision 对排序后的人工 blob 图 JSON 求哈希；正式规范须固定编码、字段及缺失表示，不能直接采用 JS 对象顺序作为跨语言契约。Read 工具展示文本为针对该人工夹具的简化投影。

## 实际做过的实验

运行方式（原重建工作区，有已有 node_modules / artifact）：

```powershell
& './offline/vendor/node/win32-x64/node.exe' .scratch/troop-history-import/probe.mjs
```

[probe.mjs](probe.mjs) 仅使用已生成的人工夹具和仓库代码，创建新的 `.tmp-history-import/PROTOTYPE-*` 数据库，不读取个人 profile。结果见 [observations.json](observations.json)。

| 实验 | 本轮结果 | 限制 |
|---|---|---|
| 三类 blob 写入真实 SQLite schema，关闭后只读恢复 | 4/6/5 行可读；内容哈希相符；读取前后 db 哈希相同 | 人工 db，无并发 writer，不证明真实 WAL 快照一致性 |
| store.db 元数据 hex(UTF-8 JSON) 与固定根槽 | 原 schema 建库；读取 kv.metadata 后定位固定根；无密钥字段保持缺失 | 人工记录，无旧版本迁移覆盖 |
| protobuf 未知字段 | 二进制往返保留一个未知字段；JSON 投影丢失该字段 | 一个人工未知字段，不证明全部版本兼容 |
| 原 artifact 加密类人工向量 | 正确 key roundtrip；错误 key 与改 tag 被拒；decrypt-only fallback 可用 | 仅截取、执行已审阅类及最小辅助函数，未启动 host；不证明当前生产链使用该类或所有远端数据使用该格式 |
| 页面纯状态模型演练 | 重复导入仍 1 条；内容变化在 1 个会话下保留 2 版；当前版本保持旧版，手动选择新版后草稿引用随之改变；缺密钥不提交；部分确认后可导入；失败批次保留此前记录 | Node 中执行纯模型，无 DOM；没有新增测试套件 |
| 浏览器实际呈现 | 未验证 | 浏览器工具拒绝 file:// 协议；未改用其他通道绕过；需要用户本地打开评估 |

加密证据来自 `src/app/dist/host/host-main.cjs:542135`：SHA-256(UTF-8 key 字符串) 派生 AES-GCM key，12 字节 IV 前缀后接 ciphertext/tag；调用不传 AAD。**不是**将 hex key 字符串直接解码为 32 字节密钥。原 artifact 区域哈希在 observations 中。实验未输出密钥、密文或真实用户内容。

## 子代理核查发现的风险

- `source/packages/agent-kv/agent-store.ts:148` 的元数据 deserialize 会填入随机默认密钥，不能用于“原密钥可用性”判定。
- `source/host/extensions/session/production.ts:174` 使用固定根槽，`session-paths.ts:11` 定义其值；不能套用所有 ID 都是内容哈希的假设。
- `source/host/agent-isolation/conversation-blob-store.ts` 直接保存本地字节；打开数据库的组件可能迁移/修复，因此原件探测需另走只读读取。
- `source/host/agent-isolation/conversation-blob-gc.ts` 有意跳过摘要归档及用户历史回链；迁移闭包必须单独设计。

## 尚未关闭的验证项

真实旧历史/跨版本导出、SQLite/WAL 一致性、加密数据来源及密钥归属、完整引用闭包、跨来源身份关联、真实目标数据库事务/中断恢复、导入 UI 仍未验证。用户未提供私人数据不妨碍讨论报告与恢复规则，但不能据此宣称完成真实数据兼容。

用户在原型讨论中授权“你觉得最好的方案进行处理”。据此确定双维度报告、每批次一次部分恢复确认、同源幂等去重，以及按会话分组、保留旧当前版本并允许人工选择的冲突处理；不再要求重复确认这些取舍。中间格式的具体编码和生产兼容验收仍须后续实现验证。此文是方案附件，不是第二套任务状态源，任务状态以 GitHub 为准。
